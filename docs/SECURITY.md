# Безопасность и публичный запуск QuestKeeps

## Гостевые ссылки и подтверждение почты (1.16.1)

- Владелец может получить стабильный подписанный адрес через `GET /api/trips/:id/share`. HMAC-SHA256 использует ключ шифрования с отдельным префиксом назначения, ID поездки и текущий `share_hash` как маркер отзыва. Это не раскрывает исходный секрет старой ссылки и не отключает ранее выданные ссылки. Смена маркера при замене/отзыве отключает и старые, и подписанные варианты. Смена ключа шифрования также инвалидирует подписанные адреса.
- Проверка подписи выполняется на сервере с постоянным по длине сравнением. Получить ссылку может только владелец; гостевой токен не даёт доступа к настройкам, участникам или управлению ссылками. API-пути `share`/`invites` также редактируются в журнале Nginx.
- Одноразовая ссылка подтверждает email и после явного нажатия кнопки может создать обычную сессию. Токен погашается и сессия создаётся в одной транзакции. Повторное использование не создаёт сессию. При уже открытом другом аккаунте адрес подтверждается без замены текущей сессии.

## Статус

Аудит исходников ревизии8de2dfe от22октября2026 выявил четыре кандидата: устаревшее React-состояние после смены пользователя, отсутствие проверки одобрения источника в подсказках мест, bearer гостевой ссылки в постоянных browser-cache ключах, общая неограниченная очередь Wikipedia. Их независимая верификация и отдельный финальный критик покрытия остановились из-за лимита сервиса. Полный аудит и проверка готового развёртывания не завершены. Отчёт сохранён вне репозитория в рабочем каталоге этой задачи, security-audit/QuestKeeps/run-1.

В1.4.0 добавлены исправления и регрессии: полный переход документа при выходе, ранний сброс приватного состояния, защита поздних ответов и межвкладочное уведомление без секретов; общий mediaFor для поиска мест; SHA-256 ключи CacheStorage без токенов, гостевые настройки карты не записываются в localStorage, миграция старого хранилища и очистка приватного localStorage; ограничение64задач/45секунд и отмена/дедупликация иллюстраций Wikipedia. Это исправления с функциональными тестами, не завершение независимого аудита.

## Права и данные

- Случайный ключ сессии хранится в host-only HttpOnly/SameSite=Lax cookie; в БД только его хеш. Secure зависит от HTTPS APP_URL. Пароли — bcrypt12, OAuth-токены — AES-256-GCM с отдельным ключом.
- Профили, поездки, права, GPS и дружба хранятся на сервере. БД и резервные копии содержат персональные данные; шифрование OAuth не шифрует всю SQLite. Нужны ограниченный системный аккаунт и защищённый диск/бэкапы.
- Клиент получает только доступные данные. Фотопревью и обычные карточки могут кешироваться. Credentials в localStorage запрещены; не использовать названия сессий/секретных ссылок как открытые ключи.
- Дружба требует явного принятия получателем, не даёт прав на поездку; friend API выводит только публичные поля и собственные списки.
- Гостевая ссылка — bearer-capability на всю опубликованную поездку. Удаление ссылки не забирает уже просмотренные/скачанные байты.

## До открытия интернета

1. Обновить Node22.19.0: по официальному security release21октября исправленная22.x —22.23.4. Использовать актуальную поддерживаемую исправленную версию. Не менять системный runtime без отдельного согласованного обновления.
2. Настроить HTTPS, правильный APP_URL и OAuth callback, проверить Secure-cookie. Оставить Next на127.0.0.1 за доверенным proxy. Закрыть .env/.git/data/backups/logs; ограничить размеры, время и конкурентность запросов.
3. Добавить ограничения регистрации/входа по доверенному клиентскому адресу и общему криптографическому бюджету, не полагаясь только на email. Не доверять произвольным Forwarded-заголовкам. Учитывать bcrypt72байта UTF-8 при расширении регистрации/смены пароля.
4. Настроить ключи, права и сроки хранения журналов/бэкапов, удалять bearer share/invite ссылки из access logs. Проверить восстановление резервной копии отдельно от ключа OAuth.
5. Завершить независимую проверку кандидатов и полного графа зависимостей, проверить состав production-сборки и реальные настройки proxy/TLS/хранилищ. Исходники не доказывают эти параметры.
6. До добавления восстановления пароля, изменения email и удаления аккаунта отдельно спроектировать верификацию адреса, одноразовые токены, отзыв сессий, ограничения попыток и удаление производных данных. Сейчас таких маршрутов нет.

Источники: [Node21октября](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases), [Next14октября](https://nextjs.org/blog/nextjs-security-update-october-14-2026). Next16.4.2/sharp0.35.5 новее указанных исправлений, но это не полное сканирование всех advisory.

## Приватные списки профиля (1.5.0)

- `/api/profiles/:username/shared-trips` требует сессию и возвращает только названия и пересечение дат поездок, где оба пользователя — владельцы или действующие участники. Дружба и гостевая ссылка не заменяют это условие. Список собственных поездок в публичном профиле не раскрывается.
- `/api/my-media/groups` и постраничный `/api/my-media?trip=…&cursor=…` возвращают только файлы автора текущей сессии; страница содержит не больше 30 записей. Курсор не предоставляет права доступа.
- `/api/my-media/:id/preview`, `original`, `download` — отдельный авторский просмотр своих скрытых кадров и кадров после выхода из поездки. Проверяются автор файла, владелец источника и владелец аккаунта Диска; отсутствующий файл не отдаётся. Публичные/гостевые правила `/api/media` не ослаблены. Ответы закрыты от общего HTTP-кэша.
- Новые проверки с фиктивными пользователями покрывают чужие файлы, отсутствие сессии, отозванное участие, несовпадающие даты и страницы файлов с одинаковыми датами. Это функциональные проверки, а не завершение независимого аудита безопасности.

## Навигация (1.6.0)

Кнопка возврата использует историю браузера с проверкой возможности вернуться внутри текущего сайта. Политика `Referrer-Policy: no-referrer` сохранена. В собственном пространстве `history.state.questkeepsNavigation` находятся только версия формата, флаг возврата и имя раздела; URL, гостевые ключи и данные аккаунта туда не копируются. Дополнительных записей в localStorage или sessionStorage нет. В старых браузерах без Navigation API при отсутствии надёжной истории используется главная страница. Состояние интерфейса не заменяет серверную проверку прав.
