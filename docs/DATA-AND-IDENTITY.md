# Данные, вход и подготовленная почта

Проверено по коду 22 октября 2026, версия 1.8.0. Это проверка хранения и сценариев входа, а не заключение о полной безопасности публичного развёртывания.

## Что уже было

Серверная база SQLite находится по DATABASE_PATH (по умолчанию data/travel.sqlite). Бэкенд — обработчики Next.js API в lib/api.ts, доступ к данным — lib/db.ts и серверные модули. Пользователи, хеши паролей, сессии, участники, поездки, друзья, OAuth-состояния и метаданные файлов хранятся в таблицах. JSON в отдельных колонках используется для кэшей геометрии/EXIF; JSON-файлов вместо базы нет. Оригиналы фотографий остаются на Диске.

SQL-параметры передаются через подготовленные запросы. Включены foreign_keys, WAL и busy_timeout. Запись нескольких связанных сущностей выполняется транзакцией. Проверки владельца/участника/дат выполняются сервером. Пароли — bcrypt; сессии — случайная HttpOnly/SameSite-cookie, в БД только её хеш. OAuth-токены зашифрованы AES-GCM. SQLite-файл целиком не зашифрован: email и метаданные доступны администратору файловой системы. Доступ к data и резервным копиям должен ограничиваться сервисным пользователем; их нельзя публиковать.

## Миграции

lib/migrations/001-baseline.ts сохраняет исходную схему и преобразования. 002-identity-mail.ts добавляет приватную почту провайдера, состояние подтверждения, одноразовые токены и очередь доставки. lib/migrations/index.ts применяет версии в одной IMMEDIATE-транзакции, фиксирует schema_migrations и user_version, отказывает при более новой схеме. Старый user_version=1 принимается без пересоздания данных.

Применение: npm run migrate. При запуске API/воркера миграции также выполняются автоматически. До обновления рабочей БД: npm run backup. Проверка: npm run health. Понижение версии схемы автоматически не выполняется; восстановление — из проверенной резервной копии с совместимой версией приложения.

SQLite подходит текущему одному серверу и его воркеру. Для нескольких серверов нужна общая серверная БД и перенос миграций, а не копирование SQLite между машинами. Каталог data должен быть постоянным томом. Резервное копирование использует SQLite backup API, поэтому не копирует один лишь файл без WAL.

## Связанный Яндекс

Связь задаётся уникальным accounts.yandex_id и accounts.user_id. Вход через уже связанный Яндекс использует этот user_id; совпадение отображаемого имени или email не является основанием для автоматического объединения. Чужую существующую привязку перенести нельзя. Для связывания нужно войти в основной профиль и подключить Яндекс оттуда. Если почта нового Яндекс-входа совпадает с существующим обычным профилем, второй профиль не создаётся: предлагается войти в существующий и явно связать аккаунт. Если ранее созданы два независимых профиля, автоматического переноса поездок и объединения нет.

Дополнительная почта провайдера хранится в accounts.provider_email и возвращается только в собственном профиле; публичные профили и поиск её не возвращают. Для старых связей она появится при следующем входе/повторном подключении через Яндекс, без фонового запроса к провайдеру.

Исправление OAuth: нельзя смешивать прямую запись Set-Cookie и NextResponse.cookies.delete — удаление временной cookie затирало cookie новой сессии. Теперь обе cookie записываются через один API, временная удаляется с тем же Path=/api/auth.

## Подтверждение email — пока выключено

EMAIL_VERIFICATION_REQUIRED=false — текущее значение по умолчанию. Для включения позже нужны RESEND_API_KEY, EMAIL_FROM с подтверждённым доменом отправителя, HTTPS APP_URL и работающий воркер. Реальная отправка сейчас не подключена. Транспорт изолирован в sendMail, его можно заменить другим почтовым сервисом.

При включённом режиме регистрация и очередь письма записываются атомарно. До подтверждения новая учётная запись не получает сессию по паролю. Существующие аккаунты автоматически не блокируются. Ссылка действует 24 часа, случайный токен хранится хешем, одноразовое потребление выполняется транзакцией. Токен передаётся во фрагменте URL, удаляется из адресной строки и отправляется серверу только после явного нажатия кнопки. Подтверждение не выполняет автоматический вход. Повторная отправка ограничена и заменяет старую ссылку.

В delivery_jobs адрес и ссылка зашифрованы; воркер получает задания с арендами, повторяет до 8 раз с задержкой и отправляет постоянный Idempotency-Key для одного задания. После отправки содержимое очищается, старые задания удаляются через 7 дней. В журнал ошибок не попадают адреса, ссылки и ответы провайдера. Письма отправляет только настроенный воркер, не обработчик регистрации. Подтверждение почты проверяет владение адресом; полную защиту от ботов само по себе не обеспечивает.

Будущий Telegram-бот пока не подключён и не отправляет данные. Подключать его следует как отдельного потребителя события успешной регистрации/подтверждения, с секретами только на сервере. Не отправлять пароль, cookie, токены или ссылки подтверждения. Пользователей нужно уведомить о передаче регистрационного email администратору через Telegram до включения этой интеграции.

## Доступность локального сайта

Next слушает 127.0.0.1, отдельный TCP-мост — только ::1. Это поддерживает оба варианта localhost без открытия порта в локальную сеть. Незапланированная остановка веб-процесса или воркера запускает только остановившийся процесс заново через 5 секунд. Обычное завершение останавливает оба. Обновление сборки всё ещё требует короткого перезапуска; это не бесшовный продакшен-деплой.

Сбой начального запроса /api/me показывает ошибку связи и повторную попытку, а не форму входа. Изменения не переносят cookie в localStorage и не продлевают/отменяют настоящую проверку сессии.

Транспорт Resend использует официальный HTTP API и ключ идемпотентности: [спецификация отправки](https://github.com/resend/resend-openapi/blob/main/resend.yaml), [повторная отправка с одним ключом](https://resend.com/changelog/idempotency-keys). Проверки доставки выполнялись только с локальным подставным транспортом, без отправки реальных писем.

Проверка кнопки «Назад» выявила ранний клик по ещё не готовой странице. Кнопка теперь становится доступной после подключения обработчика навигации. При обновлении локального сервера нужно сначала остановить процесс scripts/serve.mjs, затем его дочерние процессы; остановка только дочернего процесса запускает его заново.

В1.8.1 кнопка «Назад» перенесена в хедер. Она пропускает вкладки и якоря одного раздела, сохраняя обычную историю браузера для системных назад/вперёд. Метаданные истории содержат только название вкладки и число шагов; адреса и секретные ссылки не копируются в хранилища. Скрытые адреса прежних документов учитываются без ослабления Referrer-Policy: [поведение NavigationHistoryEntry.url](https://developer.mozilla.org/en-US/docs/Web/API/NavigationHistoryEntry/url).


## Приглашения в друзья

Миграция 003-friend-links добавляет friend_links: один действующий SHA-256 хеш случайного 32-байтного токена на пользователя и срок 30 дней. Создание новой ссылки заменяет старую, DELETE отзывает её. GET /friend/[token] только сохраняет приглашение в HttpOnly/SameSite=Lax cookie на 7 дней и возвращает на настроенный APP_URL; HEAD не устанавливает cookie. После обычного входа, регистрации или возврата из Яндекса главная выполняет same-origin POST /api/friends/link/accept: атомарно подтверждает дружбу, учитывает существующие заявки и очищает cookie. Без сессии приглашение сохраняется; удалённые/истёкшие/свои ссылки не принимаются. Ссылки многоразовые; отзыв не удаляет уже созданную дружбу. Поездки и их разрешения не меняются. Для электронной почты с будущим обязательным подтверждением cookie остаётся до последующего входа в том же браузере.
