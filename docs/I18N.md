# Translations

Interface copy lives in `lib/i18n/ru.json` and `lib/i18n/en.json`. Both files have the same stable keys. Add or change a key in both locales.

```tsx
const { t, m, language } = useLocale();

t('common.save');
t('validation.minLength', { count: 6 });
m(errorMessage);
```

`t` accepts only keys known to TypeScript. Use semantic keys such as `auth.signIn`, rather than Russian or English phrases. Templates use named parameters (`{count}`, `{date}`), with the same names in both locales. Missing keys or parameters fail explicitly.

`m` renders application messages, including `{ key, params }` descriptors and legacy plain strings. Store keys/descriptors in validation state so messages can change with the selected language. Do not pass user names, trip titles, journal text or filenames to either translation helper: render them directly.

Outside React use `translate(key, language, params)`. `translateCurrent` is for imperative browser integrations where the document language is available; prefer `useLocale` inside components.

## API compatibility

Existing readable API fields and SQLite sync errors remain compatible. `lib/i18n/messages.ts` annotates the allowlisted application fields (`error`, `message`, `fieldErrors`, `warnings`, and source errors) with locale descriptors. It does not inspect arbitrary nested user data or geographic geometry. New parameterized API messages should provide explicit `{ key, params }` metadata.

This adapter is transitional: when the API is versioned, migrate producers to explicit message codes/descriptors and remove the Russian-text compatibility map. Unknown provider errors are kept verbatim rather than guessed or machine-translated. Parameterized API error strings are currently resolved when the response arrives; fully reactive long-lived notices should retain descriptors in state.

`tests/i18n.test.ts` checks key and placeholder parity, interpolation and preservation of user content. `e2e/i18n.spec.ts` checks stored validation errors and OAuth errors in both languages.
